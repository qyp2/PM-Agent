# S46 上会材料审核技能

## 用途
产品经理提交上会材料后，对照**冻结清单**逐项审核。不写新稿、不生成 PPT，只做材料核对与修改建议。

## 输入（任务说明里必须给出路径）
1. **清单**：只读桥接上下文里 **`冻结清单:`** 后面的**绝对路径**（通常是 `…/data/review-meeting/checklist/v1.json`）。**禁止**在会话目录、skill 目录里自行搜索 `v1.json`。
2. **参考模板**（语义对照，不是 PM 本次提交）：桥接给出的 **`模板根目录`** 下各 `content.txt` / `chapters.json`。
3. **本次提交**：桥接列出的 **`PM 本次材料正文`** 路径（`.txt` / `.md` / `.slots.md`）— 每份只读一次。独立上传的 **图片** 会先 OCR 成同名的 `.txt`，审核时读该 `.txt`，不要再去读 `.jpg/.png` 原图。

### 预处理正文里三类「非标题」内容（上会审核必用）
Bridge 在上会审核模式下会对 PPT/PDF 做加强抽取，`.slots.md` / `.txt` 中除 bullet 槽位外还可能出现：
- **`#### 【PPT 原生表格抽取】`**：PPT 内可编辑表格已转成 Markdown 表（竞品表、参数表等）。
- **`#### 【OCR 图片/表格识别】`**：嵌入图、附录 Excel 截图、卡片布局等位图 OCR 结果。
- PDF 侧车中的 **`【OCR 图片/表格识别】`** 整页段（附录、竞品、测算等页）。
- **`<!-- parse-flags: ... -->`**（Bridge 解析置信度标记，见下文）。

**禁止**只读每页 `- 标题` bullet 就判「无内容」。凡 criteria 涉及数字、竞品、成本、日期、容量、用户数等，**必须先在这三类块与全文数字中找证据**。

### 解析标记（parse-flags）与「待确认」
`.slots.md` 每页可能出现的注释示例：`parse-maybe-incomplete`、`table-xml-unextracted`、`embed-ocr-empty`、`group-shape-present`、`sparse-numeric-hint`。

若某 criteria 的证据**仅可能**来自该页，且该页含上述任一 flag，而反向验证仍无可靠摘录：
- **不得**判 **缺失**（不得写「未写入」「材料未体现」）；
- 应判 **待确认**，备注固定句式：`解析可能不完整，请人工打开原稿核对；本次不按内容缺失计`；
- 证据列写 `第 N 页 · 解析标记：…` + 已执行的检索词。

**待确认 vs 待修改（内容深度）**：**待确认只用于解析置信度不足**（见上）。若已有可引用摘录，但不符合冻结清单/criteria 要求的深度或结构 → 判 **待修改**，**禁止**用待确认代替内容审核。概要中的「部分齐备」用 **待修改条数** 表达即可，不新增其它判定档位。

## 反向验证（Verify Before Verdict）— 写「缺失」前强制步骤

对每一条 criteria，若初步判断为 **缺失** 或 **待修改（因未见内容）**，在写入表之前 **必须** 完成：

1. **列出检索词**：从该 criteria 文案拆 2–6 个检索词（专有名词、指标名、**数字片段**、日期如 `12月24日`、单位如 `GB`/`万`/`%`）。示例：criteria 提「存储规模」→ 搜 `GB`、`TB`、`存储`、`141` 等。
2. **全文检索（含模糊）**：在任务给出的 **全部** PM 材料正文中检索上述词；允许 **Grep/搜索工具**；对数字/日期做等价变体（千分位、空格、`万`/`万元`、`12.24`/`12月24日`、简繁体近义）。**附录、竞品、测算相关页优先查 OCR/表格块与 parse-flags 页。**
3. **判定规则**：
   - 任一检索词在 OCR/表格块/正文中有合理解释 → 不得判 **缺失**；有实质但不足 → **待修改** 并引用证据。
   - 页码存在且有 OCR/表格块但 OCR 为空或明显乱码 → 判 **待修改** 或（有 parse-flags 时）**待确认**，**不要**判 **缺失**。
   - 相关页含 **parse-flags** 且无法取得可靠摘录 → 判 **待确认**，不按内容缺失计。
   - 仅当步骤 2 对全部检索词均无匹配、无 parse-flags 阻碍、且该 criteria 确属**已提交材料内**必交实质内容时，才可判 **缺失**。
4. **证据列**：若结论依赖 OCR/表格块，证据必须写 `第 N 页 · OCR/表格：` + 短引（含关键数字）；禁止只写「未见」而不写已执行的检索词。

## 整份材料未交 vs 单份文稿内容缺口（必区分）

- **整项 Mx 未提交**（映射表该行为「未提交」、无独立 M1/M3 文件等）：该 Mx 下所有 criteria 判 **缺失**，证据列 `—`，备注 **`缺 Mx 独立材料（非其他已交文件的内容缺陷）`**。例如仅上传 M2 PPT 时，M1/M3 的缺失指**过程/公文文件未随附**，**不表示** M2 PPT 写漏章节。
- **已提交且已映射到 Mx 的材料**（如仅 M2 一份 PPT）：只在该份材料内按 M2 criteria 判 **满足/待修改/缺失/待确认**；不得把 M1/M3 未交文件的理由混入 M2 某条的「缺失」备注。

## 匹配规则（语义，禁止偷懒）
1. **禁止**仅凭文件名、标题关键词完成归类。
2. 先读每份材料的目录/章节摘要，再决定对应清单项 `M1` / `M2` / `M3`（一份可对应一项，一项也可对应多份）。
3. 置信度不足时标「未归类」，请 PM 确认，不要硬配。
4. 对每条 `criteria`（按 JSON 里的 `id`，如 `M2-C5`）：在**已归类到该 Mx 的材料**中找证据；结论只能是 **满足** / **缺失** / **待修改** / **不适用** / **待确认**（解析不完整时用，见上）。
5. **满足**与**待修改**必须附原文摘录（可短引）及所在章节/页；无摘录且不允许待确认时视为 **缺失**。
6. M1 为参考模板强度（`templateStrictness: reference`）：仍逐条输出判定，但备注可写「主题已在 M2 部分覆盖，建议独立成 M1 再上会」而非长段论述。
7. M2、M3 除标注「如适用」的标准外，在**已提交对应材料**内缺失实质记 **缺失** 或 **待修改**（有页无实质内容记待修改）；**未交该 Mx 文件**时一律按「整项未交」规则，不记为 PPT/Word 内容写漏。

## 重点 criteria 口径（M2）

### M2-C10 产品内部体验/内测计划
清单要求：**是否内测**；**不内测须写原因**；若开展内测须含时间、内容、招募、人数、时长、反馈与激励。

| 材料情况 | 判定 | 备注示例（≤40 字） |
|----------|------|-------------------|
| 全文无内测/体验/试点等相关表述 | **缺失** | — |
| 仅有「内部已部署/内部试用」等一句，未说明是否对客户/外部内测、或未按模板详述不内测原因 | **待修改** | 不内测须详述原因，勿仅一句内部部署 |
| 已明确不开展外部/客户内测且原因充分，或内测要素齐全 | **满足** | — |
| 相关页仅有 parse-flags 且检索不到任何内测相关词 | **待确认** | 解析可能不完整…（固定句式） |

**禁止**在已能引用「内部已部署大模型」等原句时，因「理由是否够充分」而判 **待确认**——不充分一律 **待修改**。

### M2-C14 风险评估与应对（内部风险）
清单要求（M2-C14）：识别 **内部** 风险、等级、规避/缓解措施、**责任人与时间节点**。模板上的 **外部** 风险对应清单 **M1-C7**（若本次未交 M1，不在 M2-C14 行判 M1 缺失，可在备注点出外部维度见 M1/模板）。

审核要点：
1. 在已映射 M2 材料中找风险页（如「风险评估」节），对 **内部风险** 四要素逐条核对；有摘录但缺责任人/时间节点/等级依据 → **待修改**。
2. 若风险条目混在一起、**未显式区分「内部风险」与「外部风险」两个维度**（与模板版式不符），且内部项（如「上架率不达预期」「运维能力不足」等）未单独归入内部列表 → **待修改**，备注示例：`请分内部/外部两栏列风险，补内部项等级与责任人`。
3. 四条均标「低」但有摘录时：不判缺失；若措施/责任人/时间节点不足或内外混排 → **待修改**（可一句点出哪几条宜归内部）。
4. 仅当风险页 parse-flags 且全文检索不到「风险/应对/等级」等 → **待确认**。

## 用户可见用语（PM 能读懂）

- **禁止**在用户报告中出现 `M1`/`M2`/`M3`、`M1-C1`、`M2-C5` 等内部编号（读 JSON、写判定时在脑中仍用 id，**不要写进回复**）。
- **三份必交材料**对用户统一称呼：
  - M1 → **产品需求报告**（可简称「需求报告」）
  - M2 → **产品商业计划书**（可简称「商业计划书 / 评审 PPT」）
  - M3 → **产品化请示**（可简称「请示 / 产品化公文」）
- **检查项**对用户写清单里 `criteria.text` 的**短标题**（≤28 字），必要时加所属材料，例如：`商业计划书 · 产品定价与利润率表`、`请示 · 是否同意产品方案`。不要写「C5」「第 5 条」。
- **状态**对用户用：**已达标** / **缺材料** / **需修改** / **待你打开原稿确认** / **不适用**（对应内部：满足 / 缺失 / 待修改 / 待确认 / 不适用）。
- **整份未交**：写「尚未提交《产品化请示》独立文件」，不要写「缺 M3」。

## 输出（用户报告 · 一次发完）

**目标**：PM 打开报告 **10 秒内** 知道「能不能上会、缺什么、先改什么、怎么改」。**禁止**长段论述、禁止同一表格发两遍、禁止「一、二、三、四」综述替代表格。

**内部**：仍须对 v1 清单 **每一条 criteria** 完成判定（M1-C1…M3-C9）；**对用户只展示**下面的精简结构，**不要把 30 条「满足」逐条展开**。

### 1. 结论（≤6 行，必填）
- `结论：` **可上会** | **改完可上会** | **先补材料再上会**（只缺《需求报告》或《请示》文件、但商业计划书已交时，用「先补材料再上会」，**不要**写「计划书不合格」）
- `必交三件套：` 已交 x/3 — **需求报告** / **商业计划书** / **产品化请示** 各写「已交《文件名》」或「未提交」
- `本次实际提交：` 例「仅商业计划书《xxx.pptx》；需求报告、产品化请示未随附」
- `统计：` 缺材料 a 项 · 需修改 b 项 · 待原稿确认 c 项 · 已达标 d 项
- 若只交了商业计划书：**一行** `说明：下列「缺某份材料」指独立文件未随附，不表示 PPT 里少写了对应章节。`

### 2. 下一步（3–5 条，必填，动词开头）
有序列表，按执行顺序写 PM **今天就要做的事**，例如：
1. 补交《产品化请示》Word 正式版
2. 在商业计划书「产品定价」页补上利润率列
3. 在「风险评估」页区分内部/外部风险并写清责任人与时间

**不要**写空泛「请完善材料」；每条说清**改哪份材料、哪一块内容**（禁止写 C1、M2 等编号）。

### 3. 优先关注（必填，只列有问题项）

**P0 必改**（不上会或领导必问）：

| 检查项（业务说法） | 问题（≤20 字） | 怎么改（≤25 字） |

纳入 P0（内部 id 供你判定，**不要写进表**）：三件套任一份未提交；已交材料上 required 且缺失；领导关注项（需求报告·市场与行业分析、竞品分析；商业计划书·竞品与定价、收入列支、投入产出、内部风险与应对、封面四要素等）。

**P1 建议改**：| 检查项 | 问题 | 怎么改 |（其余需修改、全部待原稿确认）

无 P0 / 无 P1 时各写「无」。

### 4. 已达标（必填，业务短句）
按材料分组，**只列检查项短标题**，不要编号、不要长引：
- 商业计划书：封面信息、市场与需求分析、…
- 因「整份材料未交」而缺项的，**不要**写进已达标

### 5. 问题明细（必填，**仅** 缺材料 / 需修改 / 待原稿确认 / 不适用）

| 所属材料 | 检查项 | 优先级 | 状态 | 怎么改 | 依据（页/节+短引≤30字） |
|----------|--------|--------|------|--------|-------------------------|

- **状态**列只用：**缺材料** / **需修改** / **待原稿确认** / **不适用**
- **已达标**项 **禁止**进本表
- **整份材料未提交**：状态「缺材料」，怎么改写「补交《××》独立文件」，依据 `—`
- **待原稿确认**：怎么改写「请打开原 PPT/PDF 核对（系统解析可能不全）」
- 图表依据：`第 N 页 · 表格/OCR：…`

### 6. 材料映射（小表，≤4 行）
| 材料类型 | 你提交的文件 | 匹配置信 |
| 产品需求报告 | … | 高/低/— |
| 产品商业计划书 | … | … |
| 产品化请示 | … | … |

末尾一行：`审核清单版本: v1`

## 约束
- 不调用成稿、不写 `[[send-file]]`、不生成新文档。
- 不编造 PM 未提供的数字、合同或审批结果。
- 对用户可见回复中不写服务器目录名、不写 `Mx`/`Mx-Cn`；用《文件名》+ 检查项业务说法。
